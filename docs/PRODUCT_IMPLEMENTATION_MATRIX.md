# Product implementation and readiness matrix

**Product:** Nomalog

**Purpose:** A current, evidence-oriented view of implemented product capabilities,
remaining work, and the proof needed before calling them complete.

**Status meanings**

- **Implemented (code):** The capability exists in the repository and has
  focused code-level coverage. This does not imply a live production rollout.
- **Partial:** A useful part is implemented, but required behavior or coverage is
  still missing.
- **Not verified:** The repository contains relevant code, but the required
  live, database-backed, or operational evidence has not been recorded.
- **Not implemented:** No complete user-facing or service workflow is present.

This matrix supersedes older status summaries where they conflict with current
code, but it does not replace live-environment validation. A passing unit test,
configured provider, or visible dashboard record is not by itself evidence that
an external integration ran successfully for the current pull request.

assessment. GitLab's selected merge requests now enter the shared on-demand

## Current dashboard guidance

- The dashboard guide is served at `/docs/dashboard`; its article content is
  defined in [`product-docs.ts`](../apps/web/lib/product-docs.ts).
- Member provisioning and review limitations are served at
  `/docs/members-and-reviews` and defined in
  [`product-docs.ts`](../apps/web/lib/product-docs.ts).
- API-provisioned membership is not an invitation: an administrator must
  provision the verified email, and the user must sign in through GitHub with
  that same email. No invitation email is sent.
- The dashboard member roster shows active/deactivated status, role, and the
  latest sign-in timestamp; role changes and deactivation are audited. It does
  not track invitation acceptance, and direct provisioning sends no invitation
  email.
- Review-dependent policies now have an application workflow. Test all review
  decisions and branch-protection behavior in a disposable repository before
  enabling ENFORCING mode for production repositories.
- Evidence marked `NOT RUN` must never be interpreted as `PASS`; verify each
  check against the current pull-request head.
- Local API and web containers have been rebuilt and smoke-tested. This
  confirms local startup and route availability only; it is not evidence of
  production deployment or live GitHub integration behavior.

## Completion gates

The following evidence is required before declaring the control-plane
implementation complete:

1. A database-backed, tenant-isolated golden path from GitHub webhook receipt
   through persisted analysis, policy evaluation, evidence, audit events, and
   published GitHub check.
2. Successful live checks for each configured security provider on the current
   pull-request head, with unconfigured providers explicitly reported as
   unavailable rather than passing.
3. Live evidence that assigned eligible reviewers can approve, reject, or
   request changes, with role-safe authorization, audit records, and correctly
   updated GitHub checks for the current commit.
4. Validate member role grants, deactivation/reactivation, last-owner
   protection, first GitHub sign-in, and audit visibility in the deployed
   organization. Invitation email and acceptance tracking are not implemented.
5. Isolated database-backed security and lifecycle tests, plus deployment
   evidence for monitoring, backup/restore, retention, and operational
   response.

## Milestone status update

This update supersedes older table text above where it conflicts with the
current implementation:

- **Enterprise identity:** OIDC and SAML provider configuration, organization
  sign-in discovery, SSO enforcement, session authentication-method tracking,
  and administrator settings UI are implemented. OIDC/SAML provider login,
  the additive database migrations, and real IdP interoperability have not
  been validated in a deployed environment.
- **Role and tenancy hardening:** The member-management UI and role hierarchy
  checks are implemented. Database-backed tenant and privilege-escalation
  tests require an explicitly configured disposable test database; they must
  not be pointed at a shared or production database.
- **Queue operations:** Worker heartbeat/stalled-event metrics, a
  token-protected internal queue operations endpoint, and a recovery runbook
  exist. The recovery procedure has not been exercised as an operational
  drill; heartbeat and queue metrics still need monitoring/alert integration.
- **Security evidence and provenance:** Evidence collection and reads are
  bound to the persisted pull-request head SHA; stale or invalid-confidence
  provenance signals are not counted as current evidence. Integrations and
  provider permissions remain uneven, and no evidence provider is treated as
  passing merely because it returned no findings.
- **Data lifecycle:** The current organization deletion flow still requires
  operator confirmation of external cleanup, and the synchronous export is
  not scalable for unbounded histories. Account-wide deletion, backup-expiry
  verification, legal holds, and data-residency enforcement are not
  implemented. The proposed controls are documented in
  [`DATA_LIFECYCLE_DESIGN.md`](./DATA_LIFECYCLE_DESIGN.md).
- **Notifications and remediation:** The worker has a daily overdue-finding
  notification and administrators can inspect/retry failed email attempts.
  Configurable multi-stage SLA escalation, provider delivery/bounce
  reconciliation, organization-mandated channels, Slack, and Teams are not
  implemented. Design requirements are in
  [`ENTERPRISE_NOTIFICATIONS_DESIGN.md`](./ENTERPRISE_NOTIFICATIONS_DESIGN.md).
- **Policy enforcement:** The worker now records whether the classic GitHub
  branch-protection response lists `Nomalog Security` as a required check.
  Missing/inaccessible configuration remains `NOT_RUN` or `UNKNOWN`; a
  `BLOCK` Check Run or visible classic rule does not prove that all effective
  GitHub rules prevented a merge, particularly where rulesets or bypass actors
  apply.
- **Legal and accessibility:** Terms and privacy content remain subject to
  operator/counsel approval; product documentation and accessibility/
  responsive behavior still need representative user validation. A local
  browser smoke check returned HTTP 200 for
  `/terms`, `/privacy`, `/docs/dashboard`, and `/docs/members-and-reviews`;
  the home page, legal pages, and dashboard guide had no horizontal overflow
  at tested 320, 375, and 768 CSS-pixel viewports. The sampled pages exposed a
  main landmark and heading, and the home page had no unnamed buttons or
  links. This is a limited automated smoke check, not a WCAG audit or
  representative user validation.

No live identity provider, GitHub branch-protection configuration, notification
provider webhook, backup restore, or legal review was performed as part of this
status update.
